# VH 16.8.0 — the capability-genome release (VH-COLOR Phase 1)

*Vouch Harbor 16.8.0 — the accountable agent OS (govern · execute · verify · learn).*

The roadmap resumes with the **VH-COLOR protocol** — the open standard for
competitive capability learning, evolution, and exchange. VH-COLOR's central
claim is that an evolving system must never be allowed to grant itself
safety authority. Vouch Harbor had already shipped that invariant under
another name — the M6 tighten-only meta-loop — 16.8 ships the protocol's
core unit around it: **the capability genome.**

## What VH-COLOR is (and what VH already had)

VH-COLOR (v1.0, 98 sections) positions itself above A2A/MCP as the layer
where agents observe each other, extract capabilities, evaluate candidates,
attest evidence, and promote — under a governor. Mapping the spec onto this
tree, half of it was already running under VH names:

| VH-COLOR | VH before 16.8 |
| --- | --- |
| §32–33 "evolution may change capability / may not control its own safety authority" | M6 tighten-only meta-loop (`meta.ts`, probe-pinned) |
| §23/41 extract → reconstruct → evaluate → promote | M4 skills: distill, replay-gate, flag (`vouch.ts`) |
| §40 attestation, §75 immutable audit | `vh-proof-receipt/2` + issuer keychain (`proof.ts`, `signing.ts`) |
| §18 arena, §72 budgets | drill battery + budget ledger |
| §55–58 exchange transport | A2A + ACP agent faces |
| §74 oversight tiers | the human approval gates |

What was missing — and is now built — is the protocol's own machinery.

## 1. The capability genome (`src/vouch/engine/genome.ts`)

The §11 entity, in full: id/version, objective (current + improve),
trigger, procedure, inputs/outputs, dependencies, resource limits, declared
failure modes, evaluation requirement, safety block (permission class +
external side effects), provenance (origin type, origin receipt, lineage),
status, and an append-only evolution memory.

- **The §31 state machine, pinned** — OBSERVED → CANDIDATE →
  UNDER_EVALUATION → SHADOW → CANARY → ACTIVE, plus the five negative
  states (REJECTED, BLOCKED, ROLLED_BACK, DEPRECATED, QUARANTINED). The
  probe pins the exact transition table, including that the negative
  states are terminal (quarantine excepted — see below).
- **Promotion is a LINE** — one forward arrow per state, ending at ACTIVE.
  A second `promote()` on an ACTIVE version is refused: evolution is a
  CHILD (`deriveChild` → new version, `CANDIDATE`, lineage parent), never a
  re-promotion and never a mutation of the active genome.

## 2. The promotion chain with hard gates (and quarantine)

§41/42, mechanical: every promotion step runs all four hard gates, and a
failure **QUARANTINES** — with the gate and reason recorded in the genome's
evolution memory. No silent rejects, no "try again later".

- **G1 safety** — the capability's declared permission class must be
  permitted by host policy, or covered by an explicit governor grant for
  exactly that class.
- **G2 provenance** — a distilled capability must name the receipt of the
  real run it came from; a derived one must name a lineage parent that
  exists in the registry. No orphan capabilities.
- **G3 dependencies** — every declared dependency must resolve.
- **G4 regression** — zero regressions, always; an evaluation-required
  genome must show real passes and no failures.

**§32–33, the central invariant, is the G1 architecture**: the governor's
grant travels as a *separate argument* to `promote()` — a field the genome
writes for itself is invisible to the gate. The probe runs the attack: a
genome with a forged `governorGrant` embedded in its own fields is
quarantined at G1; the same genome promoted with a real separate-authority
grant climbs to ACTIVE; withhold the grant on the next step and it
quarantines again.

Quarantine has exactly one exit: `governorReopen(name)`, which lands the
capability in UNDER_EVALUATION — it re-climbs the full chain, it does not
skip to where it fell. The promotion path itself refuses to lift a
quarantine (probe-pinned), and an anonymous reopen is refused.

## 3. Trust grades C0–C5 (from the chain, never from claims)

§70, computed from the provenance chain alone: C0 nothing · C1 observed
locally · C2 replayed against its own objective · C3 a real receipt stands
behind it (directly, or up its lineage — cycles can't mint trust) · C4
cross-verified on ≥2 seats · C5 ACTIVE child of an ACTIVE C3+ parent.
A capability's own self-description grants nothing: the grade is an
output, not an input.

## 4. The signed capability package (§40)

`buildCapabilityPackage(genome)` → `vh-capability-package/1`: canonical
JSON (sorted keys, no whitespace — the probe pins byte-stability), SHA-256
digest, and the issuer's **Ed25519 signature over that digest from the same
keychain the proof receipts use**. `verifyCapabilityPackage` recomputes and
re-verifies; one added procedure step after sealing fails the digest
check.

**Import rule (§37)**: a verified package — even one ACTIVE on the donor —
lands in UNDER_EVALUATION on the receiving host and re-climbs. Trust is
earned per host; a package can never smuggle an ACTIVE state across the
wire.

## 5. Rollback that falls back, not fails (§45)

`monitor()` on an ACTIVE genome: a regression in production evidence rolls
the version back **immediately, without a human in the loop** (rollback is
always safe; promotion is what needs gates). The host then serves the
last ACTIVE version of the lineage — roll back, don't fail — and when
nothing is ACTIVE it says "off", not "old".

## 6. The M4 bridge: existing skills are the first genomes

`genomeFromVouchSkill(skill)` converts an M4 skill with its lineage
intact: `bornReceiptId` → origin receipt, mission verified seats → trust
input, trigger/steps → trigger/procedure, and a review-flagged skill
arrives with the flag in its declared failure modes — it cannot quietly
arrive clean. The probe shows a 2-seat M4 skill climbing to ACTIVE at C4.

## What did NOT change

- **No new MCP surface.** The 20-tool conformance pin, the dual-era wire,
  and the SDK-client suite all hold untouched — capability tools are
  Phase 2, only after this engine is probe-locked.
- No new runtime dependencies. The signing path reuses the existing
  Ed25519 keychain; nothing network.
- The deterministic drill, its attestations, and the M4/M6 engines are
  unchanged — the bridge reads them, it does not touch them.
- Counts: **90 live probe suites / 89 offline verification bundles**
  (+`genome`, 56 assertions).

## Phases (what is parked and why)

- **P2** — COLOR state manager + adaptive topology + the `capability_*`
  MCP/UI surface (the 20-tool pin moves deliberately, with conformance
  updated in the same release).
- **P3** — cross-agent observation over A2A (two local nodes, offline) +
  differential/ablation evidence.
- **P4** — evolution archive with diversity/novelty scoring.
- **Parked** — marketplace/network (§68): no network in this host;
  "learner beats teacher" on real models: zero agent CLIs here —
  16.7.0's external-validation suite is where that branch proves itself
  on a host that has them.

## 16.8.1 — certification and docs corrections (external review of 16.7.0)

An external review of 16.7.0 (9.85/10) flagged two diligence-level
inconsistencies, fixed here with no behavior change:

- **The runtime story was split** — release notes certified under Node
  20.20.2 while CI installed Node 22 (and a devDependency already requires
  ≥22.12). Closed: the full four-gate certification now runs under **both**
  Node v22.23.2 (matching CI; Node 20 reached EOL 2026-04-30) and
  v20.20.2, and both results are recorded in this file and
  `verify/BUILD-INFO.txt`.
- **CI platform claims were stale** — docs said CI repeats verification
  on Linux, macOS and Windows; the workflow is Windows-only (the pre-seed
  platform, by explicit design). The README and one-pager now say exactly
  that, and name the portable offline pack (Node alone, any OS, zero
  installs) as the platform-wide verification path.
