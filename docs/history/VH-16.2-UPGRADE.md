# Vouch Harbor 16.2.0 — the MCP capability router (M3)

**The release where Vouch Harbor becomes callable.** From this build, any MCP
client — Claude Desktop, an agent harness, your own tooling — can list and
call the product's capabilities over stdio, and every call is routed through
the same governed pipeline as the chat face. The capability router is not a
new door with a new set of rules; it is the same throat, dressed for a
standard protocol.

## What shipped

### M3 — the MCP capability router

- **`tools/mcp.mjs`** — the stdio entry (`npm run mcp`). Newline-delimited
  JSON-RPC 2.0, MCP protocol (wire-compatible with current clients at
  `2025-06-18`, design aimed at the 2026-07-28 direction — see below).
- **`src/vouch/engine/mcpRouter.ts`** — the protocol layer: `initialize`,
  `tools/list`, `tools/call`, standard errors (`-32601`, `-32700`).
- **`runVouchToolCall` (in `src/vouch/engine/vouch.ts`) — the single
  governed executor.** Every face (chat, MCP) reaches the capability tools
  through this one function: authorize (known tools only — refusals in
  words) → SIMULATE (risky) → the HUMAN GATE (risky) → the real tool →
  VOUCH (a receipt). There is no second route; a client cannot bypass the
  pipeline by choosing a different door.
- **16 governed tools** over the wire:
  - *safe* — `calculator`, `clock`, `search`, `web_search`,
    `memory_save`, `memory_recall`, `preference_save`, `workspace_list`,
    `system_info`
  - *risky* — `workspace_write`, `dispatch_mission`
  - *control/audit* — `approve_action`, `deny_action`, `call_status`,
    `mission_status`, `verify_receipt` (the gate's own tools and the audit
    reads; these are the control surface, not action calls)
- **The gate, non-blocking.** A risky MCP call returns immediately:
  `pending: true` with an `approvalId` + `callId`. The human decides from
  the Vouch UI **or** through the server's own `approve_action` /
  `deny_action` tools; `call_status` polls `gated → running → done`.
  (An MCP tool call must not block waiting for a human — and a human
  decision is a first-class, auditable event either way.)
- **Receipts are never optional.** Every COMPLETED call — success, denial,
  refusal, error — mints a receipt whose `vouch.session` / `vouch.verdict`
  events carry the calling face's `origin` (`"mcp"`). `verify_receipt`
  re-verifies any of them offline (chain + seal + issuer).
- **`dispatch_mission` runs the REAL Mission Loop.** Approved dispatches
  mint a mission ID, run the real loop on the host crew, land in the
  unified mission ledger (`mission_status`), and mint their receipt at
  loop completion — chat parity, no special path.
- **Committed engine bundle** `tools/mcp-engine.mjs` (esbuild → node ESM,
  self-contained; `npm run mcp:build` rebuilds it). `probe/mcpRouter`
  byte-pins it: a stale bundle fails the gate.

### The 86th probe — `probe/mcpRouter.test.ts`

Three levels of pinning:

1. **Engine** — `runVouchToolCall` in-process: a safe call acts and vouches
   (origin `"mcp"` in the receipt; offline verification passes); a risky
   call pauses at the gate (pending + approval handle, tracked
   `gated`); a denial executes nothing and the DENIAL is vouched
   (verdict `denied`, the SIMULATION event present, receipt verifies);
   an approval executes and vouches; an unknown tool is refused in words
   and the refusal is vouched.
2. **Protocol** — the real `tools/mcp.mjs` spawned as a child process over
   real stdio: `initialize` negotiation + server identity; `tools/list`
   (16 tools, schemas, honest risk labels); a safe `tools/call` whose
   receipt then verifies over the wire; unknown-tool refusal
   (`isError` + named refusal); the FULL denial flow (pending →
   `deny_action` → `call_status` → vouched denial, receipt verifies);
   the FULL approval flow (pending → `approve_action` → `call_status`
   → executed + vouched, file actually in the workspace); a REAL mission
   loop dispatched over the wire (gated → approved → completed with the
   real crew report → receipt verifies → mission in the unified ledger);
   `system_info`; JSON-RPC `-32601`.
3. **Freshness** — the committed engine bundle is byte-identical to a
   fresh rebuild (same discipline as the offline pack).

## Alignment with the MCP 2026-07-28 specification

The 2026-07-28 spec revision (released while this was in flight) moves MCP
to a **stateless protocol core**: no `initialize`/session handshake,
self-describing requests, explicit handles instead of hidden transport
state, poll-based long-running **Tasks**, and header-based routing. M3 is
built to that direction even though the wire speaks the current
`2025-06-18` surface (so every client works today):

| 2026-07-28 direction | How M3 embodies it |
|---|---|
| Stateless, self-describing requests | Every JSON-RPC message is self-contained; there is no transport session to hold open. Server state is the product's own session, which is per-process and labeled as such. |
| Explicit handles over hidden session state | The spec's own guidance — "mint an explicit handle from a tool and have the model pass it back as an argument" — is exactly the gate contract: `approvalId` + `callId` ride in the tool text and are threaded through `approve_action` / `call_status` by the client. The model can see the handles. |
| MRTR / `input_required` (a tool needs the user mid-call) | The human gate is the same semantic on the current wire: the call returns a pending state with what it needs (the decision), and a later call (or the UI) completes it. |
| Tasks (poll-based `tasks/get`) | `call_status` / `mission_status` are the poll-based long-running surface: dispatches run in the background and are polled to completion. |
| Authorization hardening | Transport-level OAuth is out of scope for a local stdio server; M3's authorization is application-level and deliberately stricter — a per-call human gate with the decision sealed in the receipt. The two layers compose rather than compete. |

When a 2026-07-28 wire becomes the practical client reality, the delta is
the handshake surface (retire `initialize`, add `server/discover`), not the
governance core: `runVouchToolCall` is transport-agnostic by design.

## Known labels (plain)

- **One process is one face.** The MCP server's engine state is its own
  (node-safe in-memory store); the native app's session is separate. No
  silent shared state between faces.
- **The brain is still the labeled simulation** — the `TeammateBrain`
  seam (a real model, local-first) is unchanged.
- **The Tauri native shell** is not built in this environment (no Rust
  toolchain); CI runs `cargo check` / `cargo test` / `clippy` on the
  crate. The MCP face is Node-standalone and runs anywhere Node runs.

## Upgrade notes

1. Run `npm run mcp` (or `node tools/mcp.mjs`) to start the server; wire
   it into any MCP client with stdio transport.
2. Risky MCP calls never block: approve/deny from the UI or from the
   server itself, then poll `call_status`. Every completed call carries a
   receipt id.
3. Existing installs need no migration; nothing on the wire moved. New
   receipts minted through the MCP face carry `origin: "mcp"` in their
   session/verdict events.
