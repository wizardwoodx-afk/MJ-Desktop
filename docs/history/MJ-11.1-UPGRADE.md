## 2. The version-drift close — why this ledger exists

When 11.1.0 landed, the bump touched `package.json` and `src/version.ts` but left
`package-lock.json` (both fields) and `src-tauri/Cargo.toml` at 11.0.0, left four shipped
documents titled "MJ 11.0", and never wrote this file. The `versionDrift` probe — built in V9
specifically so this failure class cannot ship silently — failed loudly, as designed, and
`npm test` went from 36/36 to 33/36.

**11.1 fixes the tree, not the probe.** In this release:
- `package-lock.json` top-level and `packages[""]` → **11.1.0**
- `src-tauri/Cargo.toml` → **11.1.0** (`src-tauri/tauri.conf.json` and `src/version.ts` already agreed)
- `README.md`, `DESKTOP-NATIVE.md`, `INSTALL-ON-LAPTOP.md`, `LOCAL-WORKLIST.md` re-titled to 11.1
- This file exists, named `MJ-11.1-UPGRADE.md` per the probe's contract
- One stale probe string corrected: `controlPlane` still matched the pre-fix spelling
  `&lock_db(&state)` while the code was properly fixed to `&*lock_db(&state)` (MutexGuard
  deref, commit `04b75c9`) — the probe now matches the shipped code.

**Result:** 36 / 36 probe suites pass, `tsc --noEmit` exit 0, `vite build` exit 0. Each
manifest now states the same version the app displays.

## 3. The Rust side — what CI was red on, and what 11.1 fixes

CI had never run the full `cargo test` until this release, and it failed on **all three OSes**
(exit 101 at the test step). Three genuine defects, all fixed in source:

1. **An orphaned V6 test.** `tests/v6_organization.rs` called `mj_desktop_lib::organization::*`
   — a module that no longer exists anywhere in the crate (the persistence layer was rewritten
   into `db.rs` in V6→V11). The test target could not compile, so `cargo test` aborted before
   running anything. The test was **replaced** by `tests/store_integration.rs` — 11 tests that
   exercise the module that actually ships: schema presence + idempotence, workflow graph
   round-trip verbatim, the chronological execution/event append log, scoped+ranked memory
   search, skill-usage counting against the *production* bootstrap (`db::open`, which adds the
   `use_count` columns that bare `db::init` does not — the difference was caught by the test),
   the approval gate opening and then gating, the dead-letter queue resolving in place,
   evolution decisions persisting, suites/evaluations round-tripping, and the MCP seed being
   once + removable.
2. **`validate_graph` alias asymmetry.** The validator accepted `type` **or** `definitionId`
   for nodes but only `from`/`to` for wires — while MJ's own tools (`connect_ports`,
   `disconnect_ports`) write and read `sourceNodeId`/`targetNodeId`, and the module comment
   claims both shapes are accepted. Every wire written by `connect_ports` came back
   `incomplete_wire`, so the verify phase failed. Fixed: both endpoint shapes accepted; a wire
   is only incomplete when *both* shapes lack an endpoint.
3. **Empty graph was a warning, not an error.** `validate_graph` reported
   `{"nodes": [], "connections": []}` as a warning, so `ok: true` — and `run_workflow` queued a
   run for a graph with nothing to run. The test harness (`run_workflow_queues_a_real_row_and_refuses_an_invalid_graph`)
   demands refusal, and the module's own docstring lists "it has nodes" as a check. Fixed:
   `empty_graph` is an error and the queue refuses it.
4. **The sandbox canary measured the wrong boundary.** `sandbox.ts` ran its "write outside the
   workspace" canary at `dirname(workspace)/mj-sandbox-canary.txt`. But mission workspaces are
   created *inside* `os.tmpdir()`, and the bubblewrap/Seatbelt profiles deliberately keep
   session temp writable — so the canary wrote to exactly the area the sandbox is *supposed* to
   allow, exited 0, and the canary failed. The canary now targets the read-only filesystem root
   (`/mj-sandbox-canary.txt`), the boundary the profile actually seals; with bwrap's user-namespace
   uid-0 mapping the canary only passes when the `--ro-bind / /` seal is genuinely present.
5. **Clippy zero-warnings.** `cargo clippy --all-targets -- -D warnings` (CI step) flagged 9
   pre-existing warnings in shipped files (2 `iter().cloned().collect()` in `control_mcp.rs`,
   6 useless `rusqlite::Error` conversions in `db.rs`, a needless borrow in `git_core.rs`, a
   doc-comment blank line). All fixed; the gate is clean.

**Results, all measured here:** 29 shipped-code unit tests (`control_mcp` + `git_core`) pass,
11 store integration tests pass (40/40), clippy `-D warnings` clean, `tsc` clean, 36/36 probe
suites pass, production bundle builds.

## 5. What is NOT proven — stated plainly

- The adversarial arena, chaos bisection and mock bridge remain **simulation-labeled** until
  executed against a verified host test runner and a real git/cargo host toolchain. The labels
  are deliberate; the modules are honest about it in their own output.
- The `reviewVisibility` live-binary probe still requires real coding-CLI binaries on disk
  (Claude Code / OpenCode). It is unchanged and remains environment-gated.
- Rust-side verification (`cargo test`, `cargo clippy`) runs in CI on all three OSes from
  this release onward; locally it needs the GTK/WebKit stack (`DESKTOP-NATIVE.md`). The
  three shipped Rust modules with tests (`db.rs`, `control_mcp.rs`, `git_core.rs`) and the
  integration test were also verified here by compiling the shipped files verbatim in a
  minimal harness (same philosophy as the git_core include-in-a-thin-crate approach this
  tree has always used); the full Tauri crate's dep tree needs more RAM than a small
  sandbox has, so only CI compiles it end to end.
- 14 harnesses are registered; **two** (Claude Code, OpenCode) are verified against real
  binaries in CI. The Proof page says exactly that — it is the truth, not a limitation to hide.
