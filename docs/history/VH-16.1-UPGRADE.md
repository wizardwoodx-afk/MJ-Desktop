# Vouch Harbor 16.1.0 — clean identity, one proof line, the learning bridge

*Release notes. What changed, what is proven, and what is not. Read with
[CHANGELOG.md](../../CHANGELOG.md) and the prior history in this folder.*

## The headline

16.1.0 is the release where Vouch Harbor stopped carrying its heritage names.
"MJ" and "ROGUE" are gone from the product surface — UI, bot identity,
provenance, persistence keys, IPC channels, styles, manifests — and the proof
protocol now rides its own wire (`vh-proof-receipt/2`) while every pre-16.1
receipt still verifies through the same open verifier. On top of the clean
line, the two committed 16.1 features ship: the **learning bridge** (M4) and
the **mission timeline** (M5-lite).

One product, one version line: the single `VH_VERSION` stamps the execution
core, the control plane, the proof protocol and the native shell. No second
version line anywhere user-visible; lineage stays in these history docs.

## 1. The rebrand (and what "clean" means here)

- `src/rogue/` → `src/vouch/` (the control plane lives under the product it
  belongs to). Zero `rogue` tokens left in the tree.
- `MJ_*`/`ROGUE_*` identifiers → `VH_VERSION`, `VH_SHORT`, `VH_TITLE`.
- Identity strings: bot **Vouch**, seat `vouch-core`, team `vouch`,
  window title **Vouch Harbor**, package `vouchharbor`, native identifier
  `com.vouchharbor.harbor`, tooltip/description cleaned.
- Persistence: every control-plane key is `vouch.*.v1/v2/v3`; the IPC web
  keys and the local DB key are `vouch.*`.
- In-page IPC channels `mj://event|approval`, `mj:add-node` → `vh://*` /
  `vh:add-node`; the stylesheet `mj.css` → `vouch.css` with `vh-*`
  keyframes; generated files (`.vh-brief/`, `.kilo/agents/vh-readonly.md`);
  export filenames (`.vouch.json`, `vh-canvas`); native event names.
- **Provenance, one line:** dispatch receipts carry
  `engine: "Vouch Harbor execution core <ver>"` and
  `controlPlane: "Vouch Harbor control plane <ver>"` — the product stamps
  both planes. The reviewer's 16.0.0 flag (two version lines disagreeing
  with the history) is closed: there is now exactly one version line.

**What "clean" deliberately does NOT mean** (compatibility, not branding):

- The legacy wire tokens survive *only* where already-issued receipts need
  them: the format names `mj-proof-receipt/1|2` and the legacy published
  seal secret. The `probe/vhClean` suite pins exactly this boundary.
- Pre-16.1 persisted documents (`mj-dossier/1`, `mj-incident-dossier/1`,
  `mj-merge-attestation/1`, `mj-mission-record/1`, `mj-provenance-statement/1`
  and friends) are still **verified** by their readers — older exports
  remain valid.
- The frozen legacy pages under `src/pages/` that are no longer routed, and
  the archived history docs in `docs/history/`, keep their historical names.

## 2. The proof protocol: `vh-proof-receipt/2`

- New receipts emit `vh-proof-receipt/2` (execution core and control plane).
- **Each wire generation is sealed with the published constant of that
  generation.** `vh-proof-receipt/2` → the current constant;
  `mj-proof-receipt/1|2` → the legacy constant, which is preserved, not
  renamed. All verifiers — in-process (both planes) and the three offline
  tools (`verify-receipt.mjs`, `verify-mission-record.mjs`,
  `issue-license.mjs`) — resolve the seal constant per format from one map.
- Back-compat is fixture-pinned: a signed pre-16.1 receipt
  (`probe/fixtures/legacy-mj-receipt.jsonl`) verifies in-process and via the
  CLI (exit 0 authenticated / 3 chain-valid-issuer-self-reported), and a
  one-hex-char tamper in the chain fails with exit 1.

## 3. M4 — the learning bridge (trajectory → skill → fast path)

A mission that runs to a verified `done` leaves a **trajectory skill**:

- `dispatch_mission` skills carry real provenance — the mission ID, the
  team, verified-seat count, cycle number — so a skill never claims a
  mission it did not earn.
- Distillation is trajectory-aware: the skill's steps are the loop phases
  that actually ran, and its trigger pattern is the objective that actually
  succeeded (stem-overlap matching — the same rule for triggering and for
  the replay gate).
- The **replay gate** is real: before a candidate skill is kept, it must
  fire on its own objective and must NOT fire on an unrelated one; a
  failure lands in failure memory and the candidate is refused.
- The **fast path** is honest about risk: a recalled skill still executes
  through `authorize → simulate → approve → call → verify → receipt` — the
  gate still pauses on risky dispatches — and the run's receipt **binds the
  skill** (id + version) so the fast path is auditable.
- A skill whose live replay fails is flagged and never auto-executes again;
  the run falls back to the full cycle.

Proven end-to-end by `probe/vouch.test.ts` (M4 suite) against a **real git
repo and the real mission loop**: cycle completes 2/2 verified → skill
distilled with the real mission ID → coarse candidate refused → second
matching mission fast-paths, receipt binds the skill, receipt verifies
offline.

## 4. M5-lite — the mission timeline

The Missions tab now opens each dispatched mission into its **unified
chain**: the mission's own events plus the session and verdict bookends,
rendered as a phase-by-phase timeline. One mission, one chain, one state —
the ONE-STATE LAW made visible. The skills tab shows each mission skill's
provenance line.

## 5. The new probe: `vhClean` (suite #85)

The rebrand is pinned so it cannot regress: the routed surface (shell,
routed pages, the whole `src/vouch/**` module, web entry, package and native
manifests) carries no legacy names outside the wire-compat tokens; identity
strings are Vouch Harbor; every control-plane persistence key is `vouch.*`;
the current wire is `vh-proof-receipt/2`; the legacy fixture verifies; the
offline CLI accepts both wires and rejects a tampered one.

## What is proven (this release's gate)

- `tsc --noEmit` — 0 errors.
- `npm test` — **85/85 probe suites green**, including the new M4 e2e suite,
  the `vhClean` identity suite, the back-compat suites (legacy fixture
  verifies in-process and via the CLI; legacy document formats re-verify)
  and the version-drift suite (manifests, README counts 85/84, release
  notes, provenance metadata all agree on 16.1.0).
- Offline verification pack: **84 bundles** (every suite except the pack's
  own self-check), byte-pinned, re-runnable with no `node_modules`
  (`node verify/run.mjs`).
- `vite build` — clean production build.
- Native: manifest/identifier/title cleaned; the Tauri crate is unchanged in
  behavior (JS-side IPC contract only).

## What is not proven (honestly)

- The desktop build is not compiled here (no Rust toolchain in the
  certification environment); `cargo check` runs in CI.
- The frozen, unrouted legacy pages and the historical docs under
  `docs/history/` still say MJ — deliberately, as history.
- M3 (the MCP capability router) and M6 (the gated, reversible meta-loop)
  remain the next milestones; 16.1 does not claim them.

## Upgrade note

State written by 16.0.0 is forward-compatible: pre-16.1 receipts and
exported documents still verify, and the web-side storage keys that moved
(`mj.*` → `vouch.*`) carry no user data that matters across the rename in a
clean install; a fresh install is the recommended path.
