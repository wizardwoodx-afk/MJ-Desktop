# MJ 11.10 — ENFORCEMENT QUALITY (2026-09-06)

> The 9.8/10 review of 11.9.9 was explicit: stop adding features, raise enforcement quality.
> Two gaps were named. Both are closed here, and the fixes are probed on a real repository.

## Gap 1 — the gate was not tied to the merge path

11.9.9 evaluated the adversarial gate after `executeTeam()` finished: the run said
COMPLETED, the gate said BLOCKED, and nothing actually stopped. In 11.10 the gate is
evaluated **inside the runtime** (`teamExecutor.gateTheRun`), on the run's own measured
facts, and the report's merge record carries the verdict:

- `report.merge.gate.allowed === false` — the writers' branches do **not** merge into the
  base branch. STRICT policy: blocked until a human records an override. ADVISORY policy:
  allowed, with the failure written into the merge reason.
- The override is a real workflow: the runner emits an `approval-request` fleet event,
  Mission Control's inbox shows it, the recorded decision (`fleet.isDecided`) is what the
  merge record checks. A break-glass with an audit trail — never a silent bypass.
- The runner UI shows a **Merge Record** card: candidates, snapshot ref/sha, who provably
  reviewed it, and the gate's authority over the merge.

## Gap 2 — the gate did not prove the verifier saw the writer's work

The team runner already recorded the evidence (`SeatRecord.reviewedSha`, snapshot sha);
the 11.9.9 gate threw it away. In 11.10 the gate is **evidence-bound**:

- A verifier only counts toward cross-verification if it ran **and** its recorded
  `reviewedSha` equals the snapshot sha — "Codex ran against snapshot abc123 and approved
  it", not "Codex completed".
- Writers produced work but no snapshot was built → **unverified** (nobody can prove they
  reviewed anything).
- A verifier whose ref does not match the snapshot is named in the reasons and cannot vouch.
- The verdict carries an `evidence` record (snapshot sha/ref, writer branches, per-verifier
  match), and the receipt's `gate.verdict` event now includes `snapshotSha` in-chain.

## Also fixed

- **Mission Control honesty**: the runner now emits real per-turn fleet heartbeats
  (`onTurn` → `kind: "heartbeat"`), so stagnation detection has live signal, and
  merge-blocks produce real approval events the inbox decides.
- **docs/FUNDING.md staleness**: the 11.9.4-era numbers (43 suites / 42 bundles) are
  corrected to the current product (53 suites / 52 bundles), and the solution section now
  names the gate, the receipts and the Role Board.
- Language across README/CHANGELOG now says what is true: the gate **blocks verification
  and the merge in STRICT mode**, and records overrides — it does not kill processes.

## Gates

New suite #53 (`mergeGate`) runs a REAL `executeTeam` over a real git repository with
stubbed CLIs and asserts: cross-harness review → PASS + merge allowed + evidence bound;
same-harness review → BLOCKED + merge blocked + override required (STRICT); ADVISORY keeps
the merge open with the failure recorded; a rejecting verifier fails the gate and blocks
the merge. verifyGate +8 assertions (evidence binding, `enforceMergeGate`), fleet +1
(`isDecided`).

Certified under Node v22.23.2: fresh `npm ci`, `tsc --noEmit` 0, **53/53 live suites**,
**52/52 offline bundles** (re-run from the extracted archive), `vite build` 0.

# MJ 11.10.1 — THE COMPLETION RELEASE (2026-09-06)

> The 9.95/10 review of 11.10.0 made one correction and one piece of advice. The
> correction: MJ has a **merge authority**, not an automatic merge engine — until the
> merge commands are actually executed after the gate passes, the honest claim is "the
> gate controls whether a merge is permitted." The advice: get to real users and
> workloads; do not add random architecture features. 11.10.1 is deliberately small: it
> finishes what 11.9.9 and 11.10 started, and nothing else.

## 1 — Ed25519 issuer signatures (`mission/signing.ts`, receipts → v2)

Through 11.10, receipts were tamper-EVIDENT but not issuer-AUTHENTIC: the HMAC seal uses
a published secret, so anyone with the secret could have produced the seal. The 2026
direction (IETF ACTA signed receipts, Nobulex, AgenticRail, Provenrail, agentmark,
Sigstore agent signing) converges on Ed25519-signed, hash-chained, offline-verifiable
receipts — so 11.10.1 makes the issuer a cryptographic identity:

- A local Ed25519 keypair (`mj.issuerkey.v1` in localStorage when available, in-memory
  otherwise). The private key never leaves the machine; MJ has no server it could reach.
- `mj-proof-receipt/2`: `issuer` + `signature` — an Ed25519 signature over the FINAL
  CHAIN HASH — beside the HMAC seal (which still applies). `verifyProofReceipt` accepts
  BOTH v1 and v2 forever; a v1 receipt archived in 11.9.x still verifies unchanged.
- **The honesty rule**: when the runtime has no Ed25519, the receipt is NOT faked —
  `signature: null` with a written `signatureNote`, tamper-evident via the seal.
- **Seat identity digests**: when the run summary names a seat's harness, the receipt
  embeds `sha256(seatId|role|harness)` in-chain — deterministic, chain-bound evidence of
  which agent harness sat in which role (the MAREF "per-agent identity" idea, minus the
  infrastructure MJ refuses to add).
- Auditors get `exportIssuerPublicKeyDocument`: key id, public key, and the exact
  verification steps in plain text.

## 2 — the Merge Executor (`mission/mergeExecutor.ts`)

The gate said whether a merge was permitted; the plan said how; nothing ran it. Now:

- **Refusal policy first**: a blocked gate with no recorded override is refused; a plan
  with problems or zero steps is refused; a host without git (browser/dev preview) plans
  but reports `simulated: true, executed: false` — it never claims a merge it cannot make.
- **Real execution**: pre-flight `git merge-tree` conflict checks for every unordered
  pair BEFORE any branch is touched; steps run serialized in plan order; a failing step
  stops the run and leaves the repository exactly where git left it (no invented
  rollback); the repo's own check runs on the base branch after the last merge; cleanup
  runs only after full success.
- **The provable fact**: `rev-parse HEAD` after the merges gives the **merge-commit sha**
  — recorded in the result, in a **signed merge attestation** (`mj-merge-attestation/1`,
  Ed25519 over the canonicalized payload), and attached to the run's vault receipt as
  metadata (the receipt chain itself is closed at issuance and never re-written).
- Teams' Merge Record card gains **Execute merge**: allowed runs merge on click; blocked
  runs show the button only when Mission Control has a recorded override (labelled
  "override recorded"), and the attestation names the override.

This is what converts the wording: MJ can now say "merged only after verification, and
here is the commit" — provable from the receipt, the attestation and the public key.

## 3 — the Evidence Pack (`mission/evidencePack.ts`)

Enterprises ask for a bundle, not features. One JSON export now carries:

- every stored receipt **re-verified at export time** (a locally tampered receipt is
  FLAGGED inside the pack, never hidden), as JSONL verbatim;
- the signed merge attestations; the flat SIEM bundle; the compliance one-pager;
- the issuer public-key document; and
- the control crosswalk — EU AI Act Art. 12/13, ISO/IEC 42001 clause 8, SOC 2 CC7/CC8 —
  each naming the concrete artifact it maps to, plus a written disclaimer: a convenience
  crosswalk, NOT legal advice, NOT an audit opinion.

The Proof page gains **Export evidence pack** and **Export issuer public key**; each
receipt card shows its signature state and its merge attestation (verify + download).

## Honesty ledger for this release

- Vault one-pager updated: Ed25519 is shipped, not "on the enterprise roadmap".
- No new runtime features beyond the three above; no hosted runners, no TEE attestation,
  no new integrations (the anti-roadmap stands).
- Receipts from older runs keep verifying (v1 path pinned by probes); unsigned receipts
  state their state in writing.

## Gates

Three new probe suites: #54 `signing` (real WebCrypto Ed25519: identity stability,
sign/verify roundtrip, forged-signature and forged-key rejection, identity digests,
v1 backward-compat, JSONL preservation, public-key document), #55 `mergeExecutor` (REAL
git: allowed merge lands with a real sha; blocked gate refused; override executes and is
named; real conflict caught at pre-flight before any merge; simulated host never claims;
attestation tampering detected), #56 `evidencePack` (empty-vault honesty, re-verification
at export, tamper-flagging, attestation inclusion, crosswalk artifacts).

Certified under Node v22.23.2: fresh `npm ci`, `tsc --noEmit` 0, **56/56 live suites**,
**55/55 offline bundles** (re-run from the extracted archive), `vite build` 0.

# MJ 11.10.5 — VERIFIED AI DELIVERY V1 (2026-09-06)

> The vertical release. Research (Sept 2026) found the biggest gap MJ can own: auditors
> now question the authorship assumption behind SOC 2 CC8.1 / SOX 404 change-management
> attestations, SLSA v1.2 and NIST SP 800-218A have NO AI-authorship category, the EU AI
> Act's deployer obligations went live Aug 2, 2026 with most organizations not ready —
> and the coding tools themselves admit they lack exportable, tamper-evident audit
> trails. Expert guidance says provenance must be captured "in the layer that runs the
> agent, before the commit exists." That layer is MJ.

## 1 — Commit-bound provenance statements (`mission/provenance.ts`)

An in-toto-shaped statement per EXECUTED merge, signed by the same issuer key as
receipts and attestations:

- **Subject**: the merged base branch at the merge-commit sha — the statement is ABOUT
  the commit, so an auditor can bind it to git directly.
- **Predicate**: builder (`mj-desktop@<version>`), **materials** = the landed writer
  seats with harness + the deterministic identity digest `sha256(seatId|role|harness)`
  (chain-consistent with receipts), **verification** = gate status/tier,
  cross-verification, review-snapshot sha, per-reviewer snapshot match, **merge** =
  base sha before, merge-commit sha, steps merged, override flag, post-merge check.
- Honesty rule: no statement for simulated or refused merges — provenance exists only
  for what happened. Fields MJ cannot measure (model versions) are absent, not invented.

## 2 — The AIBOM (`mission/aibom.ts`)

The AI Bill of Materials auditors now ask for (CISA/G7 minimum-element shape):
component, roles, missions, seat identities, last-used — folded from receipts, so it is
MEASUREMENT, not self-report. Approval status comes from the user's own Role Board
declaration (owned → approved; observed-but-undeclared → not-declared; MJ never invents
policy). Model version: "not measured (CLIs do not report model versions to MJ)".
JSON + paste-ready Markdown export.

## 3 — Deployer retention floor

EU AI Act Art. 26(6) asks deployers to keep automated logs ≥6 months. MJ's localStorage
vault cannot physically guarantee storage, so it does the honest thing: a DECLARED floor
(6/12/24 months, default 6) that the vault UI shows per record ("retain ≥ 6mo (until
…)") and every evidence pack names in its manifest. Declared, not pretended.

## 4 — Evidence Pack becomes the deployer bundle

The pack now embeds the provenance statements, the AIBOM and the retention floor, and
the crosswalk gains two rows: SOC 2 CC8.1 / SOX 404 AI-authorship and the NIST
800-218A / SLSA provenance gap. One file answers "show me the evidence for your
AI-written code."

## Gates

New suites: #57 provenance (real git merge → subject digest IS the real merge sha;
authorship digests exact; Ed25519 verifies; laundered subject rejected; simulated merge
yields NO statement), #58 AIBOM (inventory, declaration-based approval, honest versions,
empty-vault honesty, Markdown), #59 retention + upgraded pack (floor semantics, pack
carries floor + AIBOM + provenance, new mappings present).

Certified under Node v22.23.2: fresh `npm ci`, `tsc --noEmit` 0, **59/59 live suites**,
**58/58 offline bundles** (re-run from the extracted archive), `vite build` 0.
