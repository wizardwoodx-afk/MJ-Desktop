# MJ 11.14.11 — THE PROVENANCE CLEANUP + TRUE RACE TEST (2026-09-07)

> The 11.14.8 review (9.85/10) named two open nits before freezing:
> stale release references in the operational docs that versionDrift did
> not catch, and a budget-race scenario that was sequential. Both are
> closed in 11.14.11 — and the drift hole is now mechanically impossible.

## What landed (over 11.14.10)

- **Release hygiene, fixed and made mechanical.** The review found the
  metadata said 11.14.8 while operational docs named older artifacts:
  `BUILD-NATIVE.md` shipped `MJ_8.0.0` installer filenames;
  `DESKTOP-NATIVE.md` and `INSTALL-ON-LAPTOP.md` opened at "MJ 11.14.1"
  and named `MJ_11.0.0` installers; `docs/PLATFORM-LIMITS.md` carried a
  stale title. All invisible because versionDrift compared only the
  `MJ X.Y` short form on title lines and never scanned bodies. All
  operational docs now name exactly the current release, and
  `probe/versionDrift.test.ts` is extended (26 → 40 assertions):
  - **Patch-aware titles** — `MJ X.Y.Z` in a title must equal the exact
    release, so "11.14.1" can never pass as "11.14.11" again.
  - **Body scan** — every operational doc (README, BUILD-NATIVE,
    DESKTOP-NATIVE, INSTALL-ON-LAPTOP, DEPLOY-VERCEL, PLATFORM-LIMITS)
    is scanned for any `MJ X.Y.Z` / `MJ_X.Y.Z` token naming a different
    release; pointers to `docs/history/*` files are masked (their
    filenames legitimately carry old versions), everything else must be
    current.
- **The budget-race scenario is now genuinely concurrent.** It was two
  sequential `reserve()` calls — which proved the atomicity property but
  raced nothing. Now 50 rounds of two async callers via `Promise.all`,
  each reaching `reserve()` after a real event-loop yield: exactly one
  admission per round, the cap never crossed, under genuinely
  interleaved execution. (The underlying design is unchanged:
  `reserve()` is a synchronous check-and-commit with no `await`, so it
  cannot double-admit — the test now exercises that under real
  concurrency.)
