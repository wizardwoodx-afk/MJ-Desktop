# VH 16.6.0 — the hardening release (conformance-pinned MCP, one throat, honest docs, reproducible benchmark)

*Vouch Harbor 16.6.0 — the accountable agent OS (govern · execute · verify · learn).*

The external review of 16.5.0 (9.8–9.9/10, "the strongest Vouch Harbor build")
asked for one thing above all: **stop adding broad architectural features for a
moment — disproportionate hardening + external proof.** This release does
exactly that, and nothing else. Four items, all probe-pinned:

## 1. The MCP conformance suite (the claim becomes a gate)

The router is hand-implemented (no official SDK), and 2026-07-28 is a
breaking spec revision — wire-compatibility is our burden. 16.6 makes that
burden mechanical instead of asserted:

- **Official fixtures, committed with provenance.** The spec's own JSON
  Schemas are committed verbatim under `tools/mcp-conformance/fixtures/`
  (`schema-2026-07-28.json`, `schema-2025-06-18.json`,
  `ext-tasks-2026-07-28.json`) with source URLs and retrieval dates in
  `PROVENANCE.md`, and **sha256-pinned on every run** — a swapped fixture is a
  fake conformance claim, and the digest makes it fail the gate.
- **Both directions, both eras.** New **`probe/mcpConformance` (89th suite,
  12 tests)** drives the REAL server over REAL stdio and validates **every
  message against the official schema definitions** — our requests
  (`DiscoverRequest`, `ListToolsRequest`, `CallToolRequest` with top-level
  `inputResponses`, tasks requests, legacy `InitializeRequest`) and the
  server's responses (`DiscoverResult`, `ListToolsResult` + every `Tool`,
  `CallToolResult`, `InputRequiredResult`, `CreateTaskResult`/`GetTaskResult`/
  `UpdateTaskResult`, the two spec'd error envelopes, the legacy
  `InitializeResult`/`ListToolsResult`/`CallToolResult`).
- **The suite found a real defect on first run** — exactly its purpose: the
  `-32021` MissingRequiredClientCapability error carried
  `data.requiredCapabilities` as an **array**, while the official schema
  defines it as a **ClientCapabilities object**. Fixed in the server, re-pinned
  in `probe/mcpRouter`, and now conformance-validated forever. The legacy
  era's in-band gate wire (IDs in text, `approve_action`/`call_status`)
  validates against the 2025-06-18 schema with zero modern leakage.
- **Evidence, not just assertions** — every run writes
  `tools/mcp-conformance/report.json` (the full per-check tally, both eras,
  both directions): customer-facing evidence.

## 2. One throat, enforced by a whole-tree pin

The 15.x "Teammate" prototype — `src/mission/teammate.ts` (1,596 lines, a
second direct caller of the mission loop engine), `src/pages/TeammatePage.tsx`
(routed nowhere since the 16.0 merge) and `probe/teammate.test.ts` — is
**deleted**. (Its behavior already lives on the Vouch face, pinned by the 16.x
suites; the git history keeps the files recoverable.) A new test in
`probe/vouch.test.ts` scans ALL of `src/` and pins the complete set of files
that touch the mission loop engine's entry point: the engine module itself,
`src/vouch/engine/bridge.ts` (the Vouch throat), and `src/pages/LoopPage.tsx`
(the original MJ engine page — a live nav face, not a Vouch-tree path). Any
future second door fails the gate with a message that names the rule.

## 3. The docs say only what the tree proves

- **The "independent audit" claim is honest now.** The one-pager no longer
  claims an artifact that is not in the archive. It states what IS in the
  tree: the security hardening driven by the September 2026 independent
  security review (recorded in `PRODUCT-PUSH-NOTES.md` — receipt issuance
  sealed into the OS keychain, dev-machine leftovers removed), and names the
  **signed audit report + reproducible external verification artifact as
  planned public deliverables — not claimed today.**
- **Version drift closed** — "current best 16.4.1" and the one-pager's
  16.5-era stamps updated; the external review's actual verdict (16.5.0 =
  strongest build to date) is what the one-pager now carries.
- **The drill's scope stays explicit in customer-facing materials:** the
  built-in drill seats are deterministic and labeled as such — the drill
  validates the runtime/governance/verification **machinery, not
  frontier-model intelligence.** The one-pager, the deck outline and the
  benchmark artifact itself all carry the line.

## 4. The reproducible drill benchmark (customer-facing evidence)

`node tools/drill-benchmark.mjs [--out report.json]` runs the full drill
catalog (guard / maths / impossible) through the REAL Mission Loop — fresh
real git repos, the repos' own test commands, the real governance arena, real
receipts — and emits a machine-readable report: per-scenario status, verified
seats, cycle, engine, the real test-output tail, the receipt id and the
canonical attestation digest, plus a single **`overallDigest`** (sha256 over
the stable fields, catalog order). New test in `probe/drill` (now 10 tests):
the CLI must run, carry the honest verdicts (passed / passed / failed — the
honest failure ships in the benchmark, never a fake pass), recompute the
`overallDigest` from the stable fields alone, and match this process's own
drill attestations **cross-process** (reproducibility, not just stability).

## What did NOT change

- No new features, no new architectural surface — per the review's direction.
- The legacy 2025-x MCP wire stays byte-stable; the 16.5 dual-era behavior is
  unchanged except the `-32021` data shape (a conformance correction).
- Counts: **88 live probe suites / 87 offline verification bundles** —
  `-probe/teammate` + `-probe/mcpConformance` keep the tally, while the two
  suites that remained grew (vouch +1 test, drill +1 test, mcpRouter re-pinned).
