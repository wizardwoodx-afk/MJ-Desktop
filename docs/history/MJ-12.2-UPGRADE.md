# MJ 12.2 — UPGRADE notes (provider precision on the Knowledge Forge)

This file exists per the probe contract (theme probe: every `MJ-x.y` ships
`MJ-x.y-UPGRADE.md`). Full notes live in `CHANGELOG.md` row 12.2.0,
`docs/history/MJ-12.2.0-POINTER.md`, and the module header of
`src/mission/knowledgeSkills.ts`.

## Why 12.2 exists — the 12.1.1 review's one open item

The 12.1.1 review (9.85/10) confirmed the renderer-safety and data-handling
fixes, then froze the release with a single remaining item: a proposal
recorded `dataHandling: "provider"` — the document went to the harness CLI's
configured provider — but not WHICH provider: Anthropic, OpenAI, a local
model, or an enterprise proxy. The reviewer's instruction: record the
provider type / endpoint class, "without pretending to know details the
harness doesn't expose."

## What changed for the user

On the Mission Loop's Knowledge forge card, when an LLM pass is selected, a
second select appears: **ENDPOINT (your declaration)** — *unsure / harness
decides* (default), *default cloud provider*, or *local model (loopback)*.
Declare what you know; MJ records it as your declaration. Every proposal that
went to a provider now carries a second chip on the card:

- `provider: Anthropic · cloud-default` — the vendor MJ assumes by default,
  and the endpoint class.
- `provider: OpenAI · local` — local-configured.
- `provider: Anthropic · endpoint unknown` — MJ cannot see the destination;
  hovering the chip explains why, in words.

Mechanical-only distillations show no provider chip — nothing went anywhere.

## What changed under the hood

- `src/mission/knowledgeSkills.ts` — new types and fields:

  - `EndpointClass = "cloud-default" | "local-configured" | "unknown"`
  - `EndpointBasis = "detected" | "user-declared" | "not-visible"`
  - `ProviderInfo { vendor, endpointClass, endpointBasis, note }`
  - `KnowledgeProposal.providerInfo: ProviderInfo | null` — null for every
    proposal whose content never went to a provider.

  Resolution is ordered by what MJ can ACTUALLY know, never a guess:

  1. **detected** — when the host supplies a `readEnv` probe and the
     harness's known override variables are readable: no override visible →
     `cloud-default` (the harness default, stated as such); a loopback
     override (`localhost` / `127.0.0.1` / `::1`) → `local-configured`; any
     other override → `unknown` with the reason written (MJ cannot tell
     where an enterprise proxy terminates); unreadable/throws →
     `unknown` + `not-visible` with the reason written.
  2. **user-declared** — the user's own declaration on the forge card
     (`cloud` or `local`).
  3. **not-visible** — the honest default: `unknown` with a note that MJ
     runs the harness with the user's environment and cannot see its
     endpoint override settings. Tauri's `cli_env` exposes only
     PATH/searched/bins to the renderer — the design matches the code.
- `src/pages/LoopPage.tsx` — the ENDPOINT declaration select and the
  provider chip (vendor · class) with the reason on hover.
- Probe: `probe/knowledgeSkills.test.ts` 44 → **56/56** (+12: vendor table,
  loopback classification, cloud-default/local/unknown/not-visible truth
  table via scripted `readEnv`, user-declared both ways, mechanical paths
  keep `providerInfo: null`).

## Honesty notes

- The vendor label is **"the harness's default when unconfigured"** — a
  labeled default, not a claim that the request reached that vendor.
- `endpointClass: "unknown"` is the truthful answer whenever MJ cannot see
  the endpoint; every such record carries its written reason.
- Nothing here changes what MJ ships to a provider: the disclosure stands
  from 12.1.1 — invoking a harness CLI sends the document in the prompt to
  that harness's configured provider; mechanical distillation is fully
  local.
