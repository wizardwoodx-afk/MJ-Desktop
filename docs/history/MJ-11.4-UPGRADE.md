# MJ 11.4 — THE LOOP AUDIT + THE SIGNAL DIET

V11.3 hardened the design system. V11.4 does two things that look unrelated and are not:

1. **A line-by-line audit of the Teams self-evolution loop and the feedback loop** — are they
   really wired end to end, and do they behave as documented? (Answer: wired, yes; behaved,
   mostly no. Two real defects found and fixed, both pinned by new probe assertions.)
2. **Finishing the design pass the feedback asked for**: the boldness of the signal red is
   retreating to interrupt-only duty, three new palettes join the system, and switching —
   themes, views, lamps — now animates, mechanically.

Plus the version-string cleanup a review of V11.3 flagged: stale `11.2.0` in the LICENSE and
README copyright, and hardcoded `11.0.0` telemetry defaults in the A2A and OTel modules.

## 0. The Teams loops: audited, two real bugs fixed

The wiring was traced end to end before anything was changed:

```
executeTeam() → real TeamRunReport
    → signalsFromSeatRecords()          (measured facts per seat)
    → evolveTeamAfterRun()              (stats fold, evidence accumulation, gates)
    → candidate (SUGGEST: queued / AUTONOMOUS: applied via applyCandidateToTeam)
    → saveCliTeams() + TeamEvoStore persisted (localStorage, mj.teamEvolution.v1)

UI "Rate this run" → applyTeamFeedback()
    → stored verbatim in store.feedback
    → queued on the seat as pendingFeedback
    → consumed into the next candidate's evidence
```

That part is real and was already pinned by `probe/teamEvolution.test.ts` (min runs, min real
runs, evidence weight, praise suppression, growth caps, superset preservation, run-count
integrity, autonomous/suggest/off modes). The audit found where the loop did NOT do what its
own documentation promises:

### Bug 1 — queued praise became failure evidence, and suppressed nothing

Run signals never carry a rating (`signalsFromSeatRecords` sets `rating: null`); the only way
a rating enters the system is the UI queue (`applyTeamFeedback`). But `evolveTeamAfterRun`
mapped **every** queued rating into weight-2 *failure* evidence — including 5/5 praise — and
praise suppression only fired on `signal.rating >= 4`, i.e. never on the UI path. The Teams
page literally prints "Praise suppresses new candidates for the next 3 runs" next to the 4
and 5 buttons. The promise was false.

**Fix**: queued rating ≤2 → evidence (as before). Rating 3 → neutral, recorded verbatim,
never weighted. Rating ≥4 → arms `praiseSuppression` for `praiseSuppressRuns` runs, exactly
like a rating carried by a run signal, and contributes zero evidence.

### Bug 2 — the feedback queue was never drained, so it double-counted forever

`pendingFeedback` was only cleared when a candidate was created. If no candidate was due,
the same queued items were re-folded into evidence on **every** subsequent run: queued
criticism inflated its weight each run, and — worse — queued praise re-armed suppression on
every fold, permanently freezing a seat the human had praised once.

**Fix**: the queue is consumed by the fold that incorporates it. (`pendingFeedback: []` on
the fold; the candidate-creation drain is retained as a no-op safety.)

### Wiring fixes alongside

- The fold now passes `simulated` through (`getHarness(seat.harness).simulated`), so a seat
  on the labelled `local-test` double can never count as a realRun — honesty rule #2 was
  enforceable before, but this caller was not feeding it.
- Feedback rows now carry the **actual run id** the evolution fold used (`runnerRunId`
  state), not a synthetic `run-<startedAt>` that matched nothing in the ledger.

### The probe grew teeth

`probe/teamEvolution.test.ts` section 11 pins the new behaviour: praise suppresses a
candidate that is otherwise due; the praise comment never appears as evidence; suppression
delays but does not silence (real failures still produce the candidate after the window);
a neutral 3/5 neither weights evidence nor arms suppression. Suite: **45 assertions green**.

## 1. The signal diet — red retreats to interrupt-only

The feedback on V11.3 was right: Nothing OS keeps red for interrupts, and inscribed painted
too much of the screen with it. V11.4, in `themes.css` (the "V11.4 — THE SIGNAL DIET"
section):

- **Primary buttons are ink, not red**: white fill / black text on inscribed (other palettes
  keep their own quieter signals). Red returns on hover states and danger buttons.
- **Big numbers are data, not alarms**: `.stat .n` reads `--text` across all nine palettes.
- **Tinted washes halved**: `--accent-dim`/`--amber-dim` 0.14 → 0.08 on inscribed.
- **The scrollbar stops shouting**: hover goes gray, not red.
- Red remains where it *means* something: the live lamp, the brand dot, active wires, focus
  rings, selection, danger. If nothing is urgent, nothing is red.

## 3. Motion — switching animates, mechanically

- **Theme switch**: `.theme-xing` rides on `<html>` for ~260ms while the palette changes;
  every surface cross-fades colour tokens (Settings → Appearance). Percussive, not fluid.
- **View switch**: the stage re-keys on page change and fades in over 180ms.
- **Instrument lamps**: the live dot and on-glyphs breathe at 1.8s; ETA segments step in
  90ms. A desk of quiet lamps.
- `prefers-reduced-motion` wins over all of it — instant steps, no breathing.

## 7. V11.4.1 addendum — the runner repair (release-layer fixes)

Review of 11.4.0 found the proof story contradicted itself: every probe passed when run
directly, but the official `npm test` started 0/37 suites on some machines and CI was red on
all three OSes. One file was responsible.

### The runner

`tools/run-all-probes.mjs` bundled each probe by shelling out:

```
execSync(`./node_modules/.bin/esbuild ${file} ... --define:MJ_ROOT="\\"${cwd}\\""`)
```

Three failure modes, all real:

1. **Windows** — `./node_modules/.bin/esbuild` is `esbuild.cmd`; an extensionless path with
   forward slashes is not executable by cmd.exe. Nothing starts.
2. **Native-bin installs** — the `.bin` entry can resolve to
   `node_modules/esbuild/bin/esbuild`, which after postinstall *is* the native ELF/Mach-O
   binary; any wrapper that prefixes `node` then tries to parse a native executable as
   JavaScript.
3. **Quoting** — the `--define` escaping breaks on any checkout path containing a space.

**The fix: esbuild is no longer spawned at all.** Each probe is bundled with esbuild's
JavaScript API (`buildSync` — same package, same flags as the README loop) and the produced
`.mjs` runs via `execFileSync(process.execPath, ...)`. No shell, no bin resolution, no
quoting; identical behaviour on linux/macOS/windows. Verified on a fresh `npm ci`:
**`npm test` → 37/37, 0 failed.**

### The other release-layer items from the same review

- **Updater placeholders removed** — `tauri.conf.json` carried a `YOUR-MJ-OWNER` endpoint and
  a `REPLACE_WITH_…` pubkey with `createUpdaterArtifacts: true`. All of it is gone; the
  plugin stays registered (inert without config). Re-enable via the Release workflow's
  one-time setup when a real endpoint and signing key exist. No Rust was edited.
- **Vite externalization warnings silenced, deliberately** — mission modules import node
  builtins behind typeof-guards (dual-used by the node-run probes); `onwarn` now acknowledges
  that one known pattern once instead of spamming it per build. Nothing else is filtered.
- **`__pycache__/` and `*.pyc` gitignored** (none are committed in this tree; the rule keeps
  it that way when evolution-service runs locally).
- Version 11.4.1 across every manifest.

### Recorded honestly

Verified here (Linux x64 sandbox, Node 22, fresh `npm ci`): `tsc --noEmit` 0 · `npm test`
37/37 · `vite build` 0 with the externalization spam gone. **Not verified here:** GitHub CI
end-to-end (the Probes step now runs the repaired runner on all three OSes; the cargo
test/clippy steps remain Rust-side and were never runnable on this machine), and the
Tauri/Rust layer generally. The repo's history remains a force-pushed single visible commit
— preserve full history going forward; a rewritten past is review friction no patch can fix.
