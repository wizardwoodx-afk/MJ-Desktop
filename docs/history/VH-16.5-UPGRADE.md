# VH 16.5.0 — spec-current MCP (2026-07-28) + the completed clean identity

*Vouch Harbor 16.5.0 — the accountable agent OS (govern · execute · verify · learn).*

Two jobs in this release, both taken from the external review of 16.4.1:
the protocol layer was not current with the newest MCP specification, and
the shipped docs/identity still described older eras.

## 1. The MCP router is now dual-era (speaks 2026-07-28 + every legacy revision)

The MCP specification released **2026-07-28** retired the
`initialize`/`initialized` handshake and `Mcp-Session-Id`: every request is
now stateless and self-describing, carrying its protocol version and
capabilities in `_meta`. 16.5 implements that spec AND keeps the legacy
wire — one server, two eras, one governed executor.

**Modern era (2026-07-28):**
- `server/discover` (the spec's required discovery RPC): supported
  versions, capabilities (tools + the tasks extension), instructions,
  `ttlMs`/`cacheScope`, server identity in `_meta`.
- No handshake required: a request with modern `_meta` is processed
  directly. Version mismatches answer **`-32022` UnsupportedProtocolVersion**
  with the `supported` list; a request missing the required
  `io.modelcontextprotocol/clientCapabilities` answers `-32602`.
- Results carry **`resultType`** (`complete` / `input_required` / `task`)
  and the server's `_meta.serverInfo`.
- **Cacheable lists** (spec MUST): `tools/list` and `server/discover`
  carry `ttlMs` (1 h — the tool set is static within a release) and
  `cacheScope: "public"`; the tool list is returned in deterministic
  (sorted) order for stable client caches.
- **MRTR (Multi Round-Trip Requests)**: a gated modern call does not block
  and does not return an opaque "pending" — it returns
  `resultType: "input_required"` with the human decision as a proper
  `elicitation/create` request in `inputRequests` plus an opaque
  `requestState`. The client re-sends the same call with
  `inputResponses` (top-level params, per spec) and the decision resolves
  the same gate — approve or deny, same executor, same receipt.
- **Tasks extension** (`io.modelcontextprotocol/tasks`): clients that
  declare the extension in their per-request capabilities get a durable
  task handle (`resultType: "task"`, `taskId`, `pollIntervalMs`) for gated
  work. `tasks/get` reflects the LIVE call track on every read
  (`working` / `input_required` / `completed` with the final result +
  receipt); `tasks/update` answers the gate; `tasks/cancel` is
  cooperative — honest about work already in flight ("a mission cannot be
  un-executed"). The extension is advertised in `server/discover` and a
  tasks RPC from a client that didn't declare it answers **`-32021`
  MissingRequiredClientCapability** with the required capability named.

**Legacy era (2025-11-25 / 2025-06-18 / 2025-03-26):** byte-stable — the
`initialize` handshake, `approve_action`/`deny_action` + `call_status`, and
the old result shapes (no `resultType`) are exactly what 16.2–16.4
clients saw. Era is determined per request: presence of a modern
`_meta.protocolVersion`.

**What is intentionally NOT implemented** (labeled, not hidden): the
HTTP-specific pieces (header routing `Mcp-Method`/`Mcp-Name`, RFC 9207 /
CIMD authorization hardening — this transport is stdio, and the spec says
stdio implementations should NOT follow the HTTP authorization
framework), and `subscriptions/listen` push (the spec makes polling the
default and notifications optional). Roots/Sampling/Logging were
deprecated by the spec and were never implemented.

Probe-pinned: `probe/mcpRouter` grows 14 → **22 tests** — discover,
sorted+cacheable modern list, MRTR retry to a verified receipt, the full
Tasks lifecycle (create → get → update → terminal completed + receipt),
`-32021`/`-32022`, and era separation (legacy wire unchanged).

## 2. The clean identity is completed on the visible surface

16.1 cleaned the control plane (pinned by `vhClean`); the review found the
legacy heritage names still present in shipped docs and visible UI. 16.5
removes them from the **whole visible product surface**:

- **UI**: the home headline ("Vouch"), onboarding ("Welcome to Vouch
  Harbor"), the canvas watermark ("VH · canvas snapshot"), the nav
  descriptions, and every page's copy (Teams, Mission, Providers,
  Evolution, V10, MCP, Mission Control).
- **Agent identity prompts**: the node library now reads "You are the
  Vouch Harbor Planner / Coder / Reviewer / …" — the agents wear the
  product name.
- **Exports**: the provenance demo generator is "Vouch Harbor" at the
  current `VH_VERSION` (was a legacy product name at a 2023-era version).
- **Config**: the ACP override env is **`VOUCH_ACP_BIN`** — the legacy
  name is still honored (read as a fallback), the same back-compat policy
  as the wire formats.
- **IPC**: the workflow package contract's `application` field moves to
  `"VH"` on BOTH sides of the bridge (TS + Rust).
- **Docs**: the one-pager (rewritten — one product, one version, one
  narrative, one capability inventory), the deck outline, the
  information-architecture map (five doors → six, matching the table that
  already recorded the change) and the platform-limits doc now describe
  16.5.0.

Pinned: a new `vhClean` test scans the entire visible surface
(`src/app`, `src/pages`, `src/panels`, `src/canvas`, `src/ipc`,
`src/browser`, `src/domain`) with the same zero-legacy-name standard as
the control plane. **The one labeled exception:** historical
developer-facing comments inside the engine internals (`src/mission`,
`src/engine`, `src/graph`) keep their provenance headers; a dedicated
identity-sweep release retires those, so the promise in the release notes
is exact.
