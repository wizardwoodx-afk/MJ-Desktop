## 1. The Rust side (the backend is real)

`src-tauri/src/commands.rs` grew:

- `cli_providers_detect` — one pass, 19 bins, PATH lookup, version sniff where cheap.
- `harness_env` — the env vars each harness needs (e.g. `GROK_CODE_XAI_API_KEY`).
- `ALLOWED_CLI_BINS` — the spawn allowlist: builtin registry ∪ saved custom harnesses.
- `harness_argv` — the canonical headless argv per id (single source for TS and Rust).
- `cli_invoke` — spawn with timeout, capture stdout/stderr, no shell.
- **Custom harness store** (`custom-harnesses.json`): `custom_harness_list`,
  `custom_harness_save`, `custom_harness_delete`, and `custom_harness_validate` —
  the SAME rules as the TypeScript validator: bin may not contain `` ;|&`$><"' `` or
  whitespace or `..`, name ≤ 64 chars, id ≤ 48, argv must contain `$PROMPT` exactly
  once, no newlines. Rust re-validates before every save; the allowlist is recomputed.

## 7. V11.6.1 — the review fixes (current)

An external review of 11.6.0 (compared against the 11.5 commit) found one real functional
gap and two incorrect CLI mappings. All fixed; nothing else moved.

### 7.1 Custom harnesses are first-class in `teamExecutor` (the hole, closed)

The review was right: `teamExecutor` still did `AGENT_CAPABILITIES[a.seat.harness]` at
three sites (preflight, `runSeat`, `unrunRecord`), which is **undefined** for
`custom:<slug>` — the advertised flow (register custom → assign to seat → run team) could
crash or misclassify. The islands are now one abstraction:

- **`resolveCaps(harness)`** (agentCapabilities.ts) — a TOTAL resolver. Builtin → its
  entry; registered custom → `syntheticCustomCaps` (bins from the spec, user argv,
  enforcedReadOnly false); unregistered custom / unknown id → an honest entry with empty
  bins. It never returns undefined.
- Consumers routed through it: `teamExecutor` (all three sites), `agentTeam`
  (`composeSeatArgv`, `validateTeam`, the advisory-read-only warning), the TeamsPage seat
  lists and the Inspector. `binPaths` is keyed `Map<string, string>`, not `HarnessId`.
- Preflight refuses an **unregistered** custom before any spawn, with the re-add message
  (`not registered (anymore)… Teams -> Connect`).
- **The probe now proves execution, not plumbing** (review fix #5): section 6 runs a REAL
  `executeTeam()` over a real git repo with a stubbed CLI — a registered custom seat
  **completes**, invoking the user's binary with the user's argv template (`run $PROMPT`),
  and an unregistered custom is refused with the re-add message. Suite: 64 ok-sites,
  70 executed checks.

### 7.2 Antigravity: the binary is `agy` (mapping corrected)

11.6.0 guessed `antigravity` + Gemini-style `-p`. The shipped CLI (Antigravity 2.0,
2026-05-19; individual-tier replacement for Gemini CLI since the 2026-06-18 cutover) is a
closed-source **Go binary invoked as `agy`** — install
`curl -fsSL https://antigravity.google/cli/install.sh | bash` (Windows:
`irm https://antigravity.google/cli/install.ps1 | iex`). Registry, capabilities, Rust
detect + allowlist + argv table all say `agy` now. The headless prompt flag stays
**community-graded** (Gemini heritage) — the Connect tab's Test button decides on your
machine; the source note says exactly that.

### 7.3 Amp: execute mode, not runner mode (mapping corrected)

11.6.0 used `amp --headless`. Amp's documented non-interactive single-shot mode is
**`amp -x "<prompt>"`** (execute mode — ampcode.com/docs/cli/execute-mode and
Sourcegraph's own CLI guide); `--no-tui` is *runner* mode, a different thing. argv is now
`["-x", "$PROMPT"]`, graded `docs`.

### 7.4 OpenHands: documented headless mode (mapping corrected)

11.6.0 used `openhands solve` (a pre-V1 design). The V1 CLI documents
**`openhands --headless -t "<task>"`**, with `--json` for a JSONL event stream (PyPI +
docs.openhands.dev). argv is now `["--headless", "-t", "$PROMPT"]` with a `ndjson` json
capability, graded `docs`. Install line updated to `pip install openhands`.

### 7.5 Not changed (review suggestions weighed)

- A `HarnessRef` discriminated-union type would be cleaner than the `custom:` string
  convention — agreed in principle, deferred: it touches every persisted team file for
  zero behavioural gain. `resolveCaps()` already gives the single choke point such a type
  would protect.
- Unverifiable-in-sandbox claims stay labelled. Every `community`-graded mapping names
  its source; the Connect tab smoke-tests the real binary on the user's machine.

**11.6.1 gates:** `tsc --noEmit` exit 0 · `npm test` 39/39 (harnesses 70) · `vite build` exit 0.

## 8. V11.6.2 — one harness truth (the consolidation pass)

The second external review compared 11.6.1 with 11.4.1 and said it plainly: 11.6.1 is the
much stronger product, but 11.4.1 remained the **cleaner baseline** — one harness truth,
no duplicated sources. It found exactly two fragments, and both were real:

### 8.1 The policy layer had drifted from the registry

`harnessPolicy.ts` still carried the OLD invocation shapes for the corrected harnesses —
Amp `--headless`, OpenHands `solve` — after `agentCapabilities.ts` had been fixed in
11.6.1. Two layers, two answers: the capability registry said `-x`, the policy layer
said `--headless`. The review's prescription: *one canonical resolved-harness object
should feed every execution path.*

The fix is structural, not string edits: **the policy layer now DERIVES its argv from the
capability registry** via `registryArgv(id, kind)` — base invocation + permission flags
come from the registry, and the policy layer keeps only what is uniquely its job (risk
classes, grant text, turn limits). 28 entries are derived; only claude / codex / opencode /
aider keep hand-tuned compositions (they add `--tools ""`, `--output-format json`,
`--skip-git-repo-check`, `--no-auto-commits` — flags the registry models as separate
capabilities), and cline / kilo / hermes keep conservative shapes, each with an inline
note saying why. Side effect: **Grok's write shape regains its documented permission
flags** (`--permission-mode acceptEdits --sandbox workspace`), which the hand-copied
policy entry had silently dropped.

### 8.2 The adapter tier gap is closed

`harnessAdapters.ts` had 8 real profiles while the registry knew 21 harnesses (25 since V11.7.1) — a
graph-mission agent pinned to `amp` got **no adapter at all**. Now:

- **19 CLI profiles** (the original 8 + all 11 registry CLIs added in 11.6, honestly
  profiled from the 2026-09 research: languages, strengths, install hints).
- **`custom:<slug>` harnesses resolve to a real mission adapter** (`CustomCliHarness`),
  built from `resolveCaps()` — `prepare()` shows the user's bin and argv; `invoke()` goes
  through the Rust custom path (TypeScript deliberately passes no argv: Rust re-expands
  `$PROMPT` from its own saved registry, the same trust boundary the team executor uses).
  Unregistered customs return an honest null.
- **`llm` is deliberately not a spawnable CLI adapter** — a direct LLM call has its own
  path in the mission runtime; faking a CLI adapter for it would be a lie.
- `acp` stays registered by `acp.ts` (the protocol adapter), `local-test` stays the
  labelled simulation double.

Arbitration needs no changes: it already filtered by `allowedHarnesses` and rejected
harnesses known to be absent — the pool just finally matches the registry.

### 8.3 Pinned so it cannot drift again

`probe/harnesses.test.ts` §7 ("one harness truth", 110 checks — suite now 180 executed):
every policy entry's base invocation agrees with the registry (first token + `$PROMPT`
exactly once; hermes exempt with a comment — in-process runtime vs CLI shim is a real
dual shape), the twelve derived ids deep-equal their registry shape, the stale
`--headless`/`solve` shapes are gone, Grok's write flags are back, every registry CLI
has an adapter, `llm` doesn't, customs adapt for real, and an `amp`-pinned graph agent
prepares `-x` for actual execution.

## 9. V11.6.3 — documentation truth + the resolver, everywhere

The third review of 11.6.2 found the architecture caught up but two release-documentation
defects remained, and left one deeper suggestion. All three addressed:

### 9.1 The registry is 21 ids, not 22 (25 since V11.7.1)

The 11.6.0 release text said the HarnessId union grew "from 15 to 22 ids" — a miscount
that survived three patch releases. The union and `HARNESSES` both contain **21** ids (25 since V11.7.1)
(19 detectable external CLIs + the vendored Hermes runtime + the direct-LLM path). Every
occurrence is corrected, and the probe now pins the count (`HARNESSES.length === 21` and
no stale count as a CURRENT claim), so a wrong count fails a gate instead of
surviving to the next review.

### 9.2 Historical version lines are explicitly historical

The §6 compatibility section ended with "Versions: 11.6.0 across all six manifests" —
true at 11.6.0, stale in a tree at 11.6.2. It now reads "at the 11.6.0 release" and
points at the current version, so a reader can tell record from present.

### 9.3 Session resolution joins the one harness truth

The review noted `sessions.ts` still consulted `AGENT_CAPABILITIES` directly with its own
custom guard — safe (it degraded customs to `continuity: "none"` with an honest warning),
but conceptually a second path. `sessionArgv()` and `sessionIdKind()` now resolve through
`resolveCaps()`: a custom harness (registered or not) is stateless by definition — the
synthetic entry carries no session shape — and an unknown id gets a "not registered"
warning instead of being mislabelled as a custom harness. Behaviour for every builtin is
unchanged; the custom warning text is unchanged (probe-pinned).
