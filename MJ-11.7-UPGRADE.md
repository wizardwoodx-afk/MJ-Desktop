# MJ 11.7 — THE VACUOUS-GATE FIX

> The 11.6.3 review said: *"Fix that one probe predicate, rerun the full suite, and then
> you have a very strong candidate for the real FINAL."* The predicate it flagged was
> real but not the deepest problem in that file. Fixing it properly meant finding — and
> admitting — a worse one of my own.

## 0. What the review found, and what was actually there

The review correctly read the shipped bytes: `MJ-11.6-UPGRADE.md` line 256 contains the
plain text `from 15 to 22 ids` (the §9.1 historical explanation of the miscount), while
`probe/harnesses.test.ts` asserted `!doc.includes("22 ids")` — so it predicted a failing
gate (188/1) and refused to call 11.6.3 FINAL.

Running the shipped tree tells a stranger story: the gate printed **189 passed,
0 failed**. Not because the assertion passed — because **it could never fail**:

```ts
const ok = (c: boolean, m: string) => { if (c) pass += 1; else { ... } };  // condition first
ok("no stale '22 ids' count survives ...", !doc.includes("22 ids"), ...)  // label first
```

The helper took `(condition, message)`. Every call site in the suite — all of them,
since 11.6.0 — passed `(label, condition, detail)`. So `c` received the **label string**,
which is always truthy. **Every check in suite #39 passed vacuously from 11.6.0 through
11.6.3.** The counts (51 → 70 → 180 → 189) were real executions with zero assertions.
The custom-team execution test ran; its assertions could not fail. That is a far worse
defect than the one the review predicted — same file, same fix, opposite symptom.

The reviewer's instinct — *"I would not ship this exact ZIP as FINAL"* — was correct.

## 1. The fix

1. **The helper now matches the call sites**: `ok(label, cond, detail)`. One line.
2. **All 189 checks are real.** The first honest run failed five of them — latent defects
   the vacuous gate had been swallowing, listed in §2.
3. **A mutation test proves the gate bites**: flipping one expectation (`21` → `22`)
   produces `188 passed, 1 failed` with a loud `FAIL` line; reverting restores `189/0`.
   This is recorded in the release session log, and the probe's header documents the bug
   so it is not quietly relearned.
4. **Every other suite was scanned** for the same reversed-argument pattern
   (boolean-first helper vs label-first calls): none have it. The 11.4.1-era suites have
   real failure histories (canvasGeometry, meridian and theme all failed during their
   authoring and were fixed) — only suite #39, written in the 11.6.0 session, mixed the
   two conventions.

## 2. The five latent failures the vacuous gate was hiding

With real assertions, the first run of the fixed suite failed:

1. **"READ_ONLY/WRITE policy covers every id — acp, llm"** — the assertion demanded
   policy coverage for `acp` (a protocol, not a spawnable CLI) and `llm` (a direct API
   call). The code was right; the assertion was wrong. It now requires coverage for
   every *spawnable* CLI id and says why acp/llm are excluded.
2. **"an UNREGISTERED custom seat is refused with the re-add message"** — the executor
   refuses unrun seats through `report.notRun`, not necessarily `report.seats`; the
   assertion only looked in `.seats`. The refusal itself was correct. The assertion now
   accepts either channel and still requires the message and no completed seat.
3. **"every non-legacy policy entry is DERIVED (≥28 entries)"** — my own count was
   wrong: 12 ids × 2 maps = **24** derived entries. The vacuous gate let the miscount
   through both when I wrote it and when I "verified" it. Now pinned at exactly 24.
4. **"no stale '22 ids' count survives"** — the review's finding, now fixed the way the
   review prescribed: **claim-precise, not phrase-banning**. The current registry claims
   must say 21; a historical mention of the old miscount is legal documentation *when
   marked as such* (the line must contain "miscount"). The doc's §9.1 prose was also
   normalized so the only "22 ids" occurrence is the marked historical quote.
5. Same class as 4: the "22 registry" phrase ban — replaced by the same claim-precise
   block.

Items 1–3 are the important lesson: **a vacuous gate does not just miss regressions, it
certifies your own mistakes back to you.** The derived-entry count (28 vs 24) was wrong
in the 11.6.2 release notes' reasoning too — the real number is stated in §8 of the
11.6 doc's correction note.

## 3. What this means for the 11.6.x release record

The architecture work of 11.6.0–11.6.3 stands (the code was independently reviewed and
its consolidation verified by reading, not just by the probe). But the *probe counts*
claimed for those releases — "51/70/180/189 executed checks" — must be read as
execution counts, not verification. `MJ-11.6-UPGRADE.md` now carries a correction note
saying exactly that at the top. From 11.7.0, the count is assertions again: **189 real
checks, 0 failed, mutation-tested.**
